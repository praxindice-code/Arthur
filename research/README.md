## Roblox cheat-defense study

### What it does (and does not do)

The top of the HTML view is a small, sourced history of Roblox security
announcements. The interactive lower half shows a single end-to-end native
pipeline: Python prepares example events, Zig validates them, Rust scores them
in order, and Python embeds **those same Rust results** in the browser page.
The threshold and consecutive-event controls change only the alert rule.
No live Roblox events are collected, and the model cannot infer real cheating
from breach incident summaries.

Large public breach catalogs belong in a separate incident-explorer section:
each row is an incident, whereas the detector requires time-ordered events
within a player or server session. Importing incident rows does not train or
validate the detector. A real telemetry adapter would need authorized,
privacy-reviewed, labeled server data and calibration against benign play.

Open `roblox-cheat-defense.html` for a source-linked timeline of Roblox's
public anti-cheat announcements and an interactive, **synthetic** simulation
of server-side gameplay signals. This is a defensive study of cheat categories,
not a guide to making cheats or a claim to have Roblox's private telemetry.
The documented milestones and simulated events are deliberately separated.

The model watches movement-rule violations, rejected client requests, reward
inconsistencies, and repetitive action timing. It is a time-homogeneous HMM.
Run the complete local path from this project folder:

```powershell
py -m bayesguard run
py -m unittest discover -s tests -q
```

`run` uses synthetic events by default. To score an authorized, normalized
local event file, use `py -m bayesguard run --input path\to\events.tsv`. Imported
sessions are unlabeled, and their IDs are anonymized in the generated HTML.
The browser view is capped at 10,000 events; it is not a large-dataset store.
The optional `roblox-demo` Bayesian alert-policy experiment remains available,
but is **not** used by `run` and is deferred from the main architecture.

The underlying probabilities are hand-set. Latency, accessibility tools,
and legitimate game mechanics can resemble suspicious behavior, so this demo
must not be used to sanction actual players. Python and Rust implement the
same Roblox-inspired HMM, and Zig validates its event frames. The viewer is
generated by Python/HTML. `run` invokes separately built native binaries;
rebuild them for your PC using [BUILD.md](BUILD.md).
The lower-level native path can also be run manually:

```powershell
Get-Content roblox-events.tsv | .\bin\normalizer.exe | .\bin\bayesguard-detector.exe --roblox 0.5 2
```

## Original cloud-audit prototype

An offline prototype for detecting suspicious sequences in simulated cloud audit
events. A time-homogeneous hidden Markov model estimates attack-stage risk after
each event. Gaussian-process Bayesian optimization chooses an alert threshold
and persistence setting on training sessions. Evaluation uses separate sessions.

The simulator and detector use invented AWS-like event names. No cloud account,
credentials, network access, or production audit logs are required.

## See what happens

Open `bayesguard-viewer.html` in a browser. It is self-contained and works
offline. Choose an attack or benign session, press Play or select an event,
and watch the risk line and the model's state estimates change. Move the alert
threshold or change how many consecutive high-risk events are required to see
when the alert fires. The shaded section marks simulated attack activity.

To generate a different set of sessions:

```powershell
py -m bayesguard visualize --seed 7 --sessions 12
```

This replaces `bayesguard-viewer.html` with the newly generated view.

## Run the experiment

Python 3.10+ and the standard library are sufficient:

```powershell
cd research
py -m bayesguard demo
py -m unittest discover -s tests -v
```

The demo prints selected settings and holdout metrics for Bayesian optimization,
random search, and a fixed policy. It also writes `demo-results.json` in the
current directory. Re-running with the same seed gives the same result.

For the checked-in run (seed 42, 160 training and 100 holdout sessions, 16
trials), Bayesian search selected threshold 0.50 and streak 2. Its holdout F1
was 0.884, compared with 0.917 for equal-budget random search and 0.857 for
the fixed policy. The random baseline did better on this split; the prototype
does not establish that Bayesian optimization improves detection.

```powershell
py -m bayesguard demo --seed 42 --train 160 --test 100 --trials 16
```

This is a research prototype. The emission probabilities are hand specified and
the simulator is synthetic, so holdout results only measure performance on this
simulator. A real deployment would need calibrated probabilities, real audit
data, data access controls, and testing against changing benign workloads.

## Components

- `bayesguard/`: simulator, online HMM, Gaussian-process optimizer, CLI.
- `rust-detector/`: standard-library Rust CLI for online inference on TSV events.
- `zig-normalizer/`: Zig utility for validating and normalizing TSV event frames.
- `bayesguard-viewer.html`: interactive offline explanation of one session at a time.

The cross-language event format is one tab-separated record per line:

```text
session_id<TAB>step<TAB>event_kind
```

The Rust CLI emits `session_id<TAB>step<TAB>risk<TAB>alert`. Build the optional
native binaries into `bin/` first; they are not committed. See [BUILD.md](BUILD.md)
for setup on another PC. Then run the sample pipeline with:

```powershell
.\run-native.ps1
```

This writes `native-results.tsv`. The test suite checks that native risks and
alerts match Python inference on the sample events.

With Zig and a Rust toolchain installed, the native pipeline can be rebuilt:

```powershell
py -m bayesguard emit --sessions 10 --output events.tsv
zig build-exe zig-normalizer/main.zig -O ReleaseSafe -femit-bin=normalizer.exe
cargo build --manifest-path rust-detector/Cargo.toml
Get-Content events.tsv | .\normalizer.exe | cargo run --quiet --manifest-path rust-detector/Cargo.toml -- 0.5 2
```

The Zig utility validates the frame shape and event names. Sessions must be
grouped, and steps must increase within a session. The Rust detector resets
its state when the session ID changes. The original Windows ARM64 binaries
were built here with Zig 0.14.1 and Rust 1.98.1. This machine prevented Zig
from spawning its embedded linker, so `entry.zig` was compiled to an object
and linked by a separate Zig linker invocation. A normal Zig installation
should use the simpler `build-exe` command above.

The preserved `build-native.ps1` is specific to the original ARM64 workspace;
its toolchain paths are not portable. Use [BUILD.md](BUILD.md) for a new PC.

## Model and tuning

The same transition matrix and emission table apply at every event step. HMM
state is reset at the start of each independent session. The risk is the
posterior probability of any non-normal state. A policy alerts after risk has
exceeded a threshold for N consecutive events. Bayesian optimization searches
the finite threshold/persistence grid with an RBF-kernel Gaussian process and
expected improvement. The objective combines session-level precision/recall,
benign false-alert rate, and attack detection delay.

The code is deliberately small enough to audit and extend. Good next steps are
realistic audit-log adapters, likelihood calibration, more varied attacks,
time-based validation, and a comparison against simpler anomaly baselines.
